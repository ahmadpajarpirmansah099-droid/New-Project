# Workspace Architecture

The application uses a shared workspace boundary so operational data can be separated between outlets while keeping a consistent application experience.

## Access model

- Access is based on the authenticated account and its assigned permissions.
- Users should only access workspaces and features granted to them.
- Frontend code must not be treated as the authority for permissions.
- Do not authorize accounts by matching email addresses in frontend code.
- Access decisions must be enforced by the backend.

## Frontend integration

- Use the application's authenticated client and verified session context.
- Never place service-role keys, passwords, or private credentials in frontend files.
- Do not use browser storage as the source of truth for business records.

## Data and module boundaries

- Business records must remain scoped to their owning workspace.
- New modules must follow the existing backend access model and preserve audit/history requirements.
- Sequential references and other shared counters must be generated by trusted backend logic.
- User interface changes must preserve the mobile-first layout and use Lucide Icons for new interface icons.

## Change control

Changes to authentication, permissions, database structure, backend functions, or data flows require review and approval before implementation. Existing business data and operational history must not be deleted or rewritten without explicit authorization.
