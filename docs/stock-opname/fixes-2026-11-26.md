# Perbaikan stok, koreksi opname, dan pembatalan invoice

## Perubahan

1. Tabel memasukkan `move_in`, `adjustment`, dan `adjustment_in` berdasarkan arah jumlahnya. Dokumen batal dan bulan lain tetap diabaikan; periode lama yang terhubung tetap dihitung, termasuk barang yang hanya tersisa pada posting historis.
2. Form koreksi memakai `counted_at` dan `physical` asli. `end` dan `result[].physical` tetap menjadi fallback untuk data lama yang belum memiliki kedua field tersebut. Isian draft yang sudah ada, termasuk angka nol, tidak dibuang.
3. `private.so_mutate` menyimpan `invoice_base_prices` per barang dalam payload stok. Harga sebelum invoice pertama dipertahankan selama masih ada invoice aktif; setelah semuanya dibatalkan, harga kembali ke nilai tersebut. Rangkaian invoice baru menangkap ulang harga master terkini, dengan penguncian baris katalog.

Tidak ada tabel, role, RPC publik, atau dependency baru. Migrasi hanya mengganti bagian fungsi yang terkait dan berhenti tanpa perubahan jika pola fungsi tidak cocok. Snapshot transaksi/opname lama tidak ditulis ulang.

## Pengujian

```sh
node --test tests/*.test.js
```

Tes UI mencakup bahan dan WIP, Move masuk/keluar/pembalikan, dokumen batal, periode lama, tanggal hitung sebelum akhir bulan maupun pada bulan berikutnya, angka fisik nol, serta pemulihan draft dan refresh tanpa membuang isian.

Jalankan SQL hanya pada database pengujian terpisah dengan skema dan migrasi yang sesuai:

```sh
psql "$TEST_DATABASE_URL" -X -v ON_ERROR_STOP=1 \
  -f tests/stock-opname-invoice-cancellation.sql
```

File ini membuat identitas/data uji sendiri, memakai role `authenticated` untuk RPC stok, dan diakhiri `ROLLBACK`. Skenarionya: dua urutan pembatalan, penghapusan harga invoice saat edit, pemulihan baseline data lama, edit data lama, invoice bertanggal mundur, harga manual sebelum rangkaian baru, dan transaksi tanpa harga invoice.

Verifikasi lokal memakai PostgreSQL 18, baseline, fungsi kalender terbaru, grant fungsi dashboard dari migrasi yang tersedia, serta skema `auth` minimal dengan identitas dummy. Ini bukan pengujian konfigurasi Supabase produksi. Jalankan juga lima suite SQL stok/kalender/dashboard yang sudah ada.

## Urutan pemasangan

1. Tinjau dan uji `supabase/migrations/20261126120000_stock_opname_invoice_price_baseline.sql` pada lingkungan uji yang sesuai dengan produksi.
2. Pasang migrasi melalui proses migrasi database yang biasa, lalu catat versinya. Jangan menjalankan file tes pada produksi.
3. Merge PR frontend melalui persetujuan pemilik. Deploy GitHub Pages tidak memasang migrasi SQL secara otomatis.

Migrasi kompatibel dengan frontend lama. Perbaikan Move dan form koreksi tidak bergantung pada field baseline invoice, tetapi perbaikan harga invoice belum aktif sebelum migrasi database dipasang.

## Batas pemulihan data lama

- Migrasi tidak menghitung ulang atau memperbaiki harga produksi secara massal.
- Harga awal data lama dipulihkan dari invoice dan snapshot awal yang masih tersimpan. Jika baris invoice awal sudah pernah dihapus saat edit sebelum perbaikan ini, riwayatnya perlu diperiksa manual; jangan menebak harga awal.
- Draft koreksi lama yang sudah berisi angka dipertahankan agar pekerjaan staf tidak hilang. Periksa angka draft tersebut terhadap hitungan fisik asli sebelum konfirmasi.
